# Evaluator Q&A (viva preparation)

**Q1. Why six agents instead of one big prompt?**
Each agent has a single responsibility with a typed input and output, so each can be tested, replaced and explained separately. Mapping and validation stay deterministic while language tasks use an LLM. A single prompt could not independently check its own output.

**Q2. How do the agents actually communicate?**
Through LangGraph's shared `RegRadarState`. Each node returns a partial update; the validator writes `pending_feedback` (a list of `ValidationDecision`s with issue codes, fields and expected values), and the synthesiser reads it on its next turn. Every exchange is also emitted as an `AgentMessage` into the additive `trace`.

**Q3. What makes the feedback loop "adaptive"?**
The conditional edge `route_after_validation` decides at runtime: finalise if nothing was rejected, revise if rejections remain and the revision budget allows, escalate otherwise. The number of loop iterations depends on the data, as `test_max_revisions_zero_escalates_immediately` shows.

**Q4. Isn't the demo just a fake trace?**
No. The trace is generated by executing the compiled LangGraph graph and is persisted from that run. In demo mode the *LLM* is replaced by a deterministic responder, whose first draft contains documented mistakes. The validator doesn't know about them and rejects them through its normal checks; revisions are computed from its feedback codes. Everything demo-generated is labelled `deterministic-demo`.

**Q5. How do you prove the loop works?**
`tests/test_feedback_loop.py::test_rejection_feedback_revision_and_revalidation_sequence` checks, on the persisted trace, the order: proposal -> rejection with structured feedback -> synthesiser receives the identical issues -> revision with `severity: low -> critical` -> second validation accepts revision 1 -> Output Agent report. `test_feedback_reaches_synthesiser_llm_through_state` repeats this with an independent scripted "live" LLM and inspects the payload it received.

**Q6. Why is the validator independent and not just another LLM?**
An LLM checking an LLM can share its blind spots. The validator re-derives facts from source data: it checks the evidence quote is a verbatim substring of the obligation, compares against the coverage matrix and known-issues register, and computes minimum severity from the obligation's features. An LLM critique is only advisory.

**Q7. How is hallucination controlled?**
(a) Extracted obligations must appear verbatim in their clause; (b) gap evidence must be verbatim from the obligation; (c) citations must match; (d) unknown obligation IDs are dropped; (e) all LLM output is validated with Pydantic.

**Q8. What happens when the LLM fails or returns garbage?**
Retries with exponential backoff, one JSON-repair prompt, then a deterministic fallback. The fallback is recorded in the trace as an error with `llm.fallback=true`, and the report states the summary source. `test_llm_failure_falls_back_and_is_reported` covers this.

**Q9. How does the Control Mapper work, and why not embeddings?**
TF-IDF cosine similarity plus keyword-phrase overlap, followed by quantitative shortfall checks (deadlines, retention, frequency). It's explainable, offline and deterministic, which suits compliance evidence. Embeddings could replace the scorer behind the same interface.

**Q10. How is remediation prioritised?**
`risk = severity_weight x urgency x exposure x classification_factor`. Urgency depends on days to the regulation's effective date; exposure is higher for incident reporting and personal data; advisory gaps get half weight. P1 >= 10, P2 >= 5, otherwise P3, with SLA-based target dates capped at the effective date.

**Q11. What data is real?**
The demo regulations and Acme Pay controls are synthetic (labelled, with "DEMO" in every ID). They are modelled on themes from real directions such as CERT-In's 2022 directions (6-hour incident reporting, 180-day log retention) and RBI's IT outsourcing direction. Live mode uses real RBI/SEBI RSS feeds or text you paste.

**Q12. Why does one gap get escalated?**
The synthesiser defends the §3.7 "should" obligation as mandatory, citing internal policy, and the validator keeps rejecting it because the source says "should". After `max_revisions` the disagreement goes to a human, which is the correct governance outcome.

**Q13. Limitations?**
Lexical mapping can miss paraphrases; RSS feeds give titles and summaries, not always full text; the control library is small and fictional; live LLM quality depends on the chosen model; there is no authentication (it's a single-user prototype).

**Q14. How would you scale it?**
Background job queue for runs, PostgreSQL instead of SQLite, embedding-based retrieval over a larger control library, per-organisation knowledge bases, authentication and role-based approval of escalations, and LangGraph checkpointers for resumable human-in-the-loop review.
